### 🔴 P0-2 根因修正：不是「租约泄漏」，是 main 库回收 worker 无法取得提交授权
- 早前结论「main 无租约 → 库最大 → 回收握手超时 → 需 doctor --fix」**部分错误**，实测修正如下：
- `agent_database_leases` 实测 10 行，**全部 owner_pid=897835（当前存活进程）、owner_start_time=146381859（与 /proc 实测一致）**，
  opened_at 分布在 11-05 07:19 → 11-07 03:03，**没有一条是 stale**。`flock` 实测该锁文件**可自由获取**（锁本身没被占死）。
- 源码定位：`dist/session-accessor.sqlite-reclamation-commit-BX3N0u2L.mjs`
  - `COMMIT_DECISION_TIMEOUT_MS = 5e3` —— 回收 worker 等 5 秒要提交授权
  - `Atomics.compareExchange(shared,0,REQUESTED,COMMITTING)` 失败即抛 "SQLite session reclamation commit checkpoint expired"
  - 授权方是**同进程另一个同步写入者**；`assertCurrent()` 校验共享库 identity 未变
- 真正卡点：**main 库 272MB（scout 85MB / coder 53MB / life 56MB）**，其中
  `transcript_events 99.4MB + trajectory_runtime_events 67.9MB + session_transcript_active_events 70714 行`
  → 回收事务持写锁时间超 5s → 授权窗口过期 → 每次都失败。
- 佐证：`main.sqlite` integrity_check=ok（**不是数据库损坏**，是时序/容量问题）；日志里 11-05 起 `agent database integrity gate` 持续出现
- 佐证：main 无 lease 但有 `clean-close receipt: written`（写入正常，**只有回收路径失败**）→ 与「回收事务太慢」完全吻合
- **结论修正**：重启 Gateway 只能清一次 stale lease（这里本来就没有 stale lease），**不解决 5s 超时**；
  真正要做的是 ① 把 main 库瘦身 ② 压缩 main 会话历史 ③ 或等上游修 COMMIT_DECISION_TIMEOUT_MS
