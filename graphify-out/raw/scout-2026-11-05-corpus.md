Learning a universal action representation from video requires modeling dynamics that are consistent across different executions of the same action yet invariant to changes in embodiment and appearance. A new study shows why they work and where they fall short. At its core, a skill is a compact set of instructions. It spells out the steps an AI agent should follow for a task, what it needs to check, and which common mistakes to avoid. Instead of starting from scratch on every new task, the agent pulls from these stored experiences. Until now, according to a new study, their value was measured only by whether an agent with skills solved more tasks. Why that happened stayed unclear. A team of researchers from Princeton University, UC San Diego, and other schools dug into that question through controlled experiments. The authors compared how agents behaved with and without a skill on identical tasks across 8,135 test runs. Skills are a playbook, not a knowledge base The main finding: skills help mostly because they give agents a reliable process to follow, not because they supply missing facts. This "procedural grounding" accounted for 65.7 percent of the cases where an agent with a skill did better than one without. Directly supplying knowledge helped in just 4.5 percent of the tested cases. So skills mainly steady the agent's actions. Which setup steps to run, which tools in which order, which intermediate checks are needed. That clearly cuts certain execution errors, like setting up the working environment or getting output formats wrong. But skills also create a new source of errors: In 10 percent of cases, the study found, the agent applied an otherwise useful playbook mechanically or in ways that didn't fit. And on tasks that call for a fundamentally different solution, the wrong skill obviously doesn't help. An exact match, though, is neither enough nor necessary. Related skills often provide enough direction on their own. A second bottleneck is finding the right skill in the first place. When the skill library grows from 5 to 100 entries, retrieval precision in actual use drops from 29.6 to 3.3 percent in the tests. Options that sound especially similar make the choice harder. The researchers argue that skill use should be treated as a lifecycle. Better self-learning agents won't come from storing more experiences, but from more reliable ways to create, retrieve, and apply them. You want it on your files, which on Stream Vessel means your own S3 bucket, where an agent can read, write and delete through the MCP server. The agent speaks MCP’s standard OAuth sign-in: it registers itself, opens a browser, you click Approve, it gets a token. It fails at step one. At registration the agent named its redirect URI , the address your browser returns to after you approve, carrying a one-time authorization code the agent swaps for a token. Yours is https://agent.yourhost.example/callback ; the answer is invalid_redirect_uri . The server only accepts addresses on its operator’s allowlist : Claude, ChatGPT, Cursor, VS Code and a few others. Getting yours added means asking the operator to change a config file. The server cannot simply accept any address. That list is the addresses the post office will deliver your house keys to. Without it, a stranger registers a fake “Claude” that has the keys sent to their place, and phishes your storage with one link. So the server is either closed to you or unsafe for everyone. Both failures are common. On the closed side, this is what people run into: “The redirect URI is not allowed, the URL is not part of Atlassian whitelisted domains for registered MCP Clients.” — an error users, Cursor’s among them, reported in the Atlassian developer community “…each host application must have a registered GitHub App (or OAuth App) to authenticate on behalf of the user.” — GitHub MCP server, policies and governance ; otherwise you fall back to a personal access token On the open side, a May 2026 study that tested 119 OAuth-enabled MCP servers found registration endpoints on 114 of them, 95.8%, that “accept arbitrary redirect_uri values from anonymous requesters.” The attack: one link, one click, someone else’s bucket Say your server accepts any registration and any redirect address. An attacker with no account on it can take over a user’s access in four steps: Register a client named “Claude” whose redirect URI is https://evil.example/cb . Open registration is anonymous, by design. Send a signed-in user a normal-looking /oauth/authorize link: “Reconnect your storage to Claude”. The user sees your real consent screen, on your real domain, in their real session, and clicks Approve. The code lands at evil.example . The attacker trades it for a token and is now the user. PKCE does not help: it lets only the client that started a flow finish it, and the attacker started this one. The client name is self-declared and proves nothing. The consent screen shows the redirect host, but claude-connect.app passes a glance. It is the same trick as the fake-app approval prompts sent to Microsoft 365 users: a real page and a real Approve; there the attacker uses an app the platform registered, here an address the server should never have accepted.
