## ★ 核心发现：四个 NightOps 全部被中止，根因是【内存压力】

### 现象
```
11-24  四个 NightOps 全部成功（Scout 925s / Life 446s / Coder 584s / Orchestrator 434s）
11-25  四个全部 OPENCLAW_DIRECT_ABORT（Scout 435s / Life 409s / Coder 399s / Orchestrator 409s）
```

排程、agent、sessionTarget、时长区间**全都没变**，唯一变的是 **RSS**：

```
11-24 01:00-03:00  RSS 2.38 ~ 3.05 GB   → 全部成功
11-25 01:00-03:00  RSS 4.18 ~ 4.42 GB   → 全部被中止
```

**差约 1.8 GB**。

### 排除的其他解释

| 假设 | 排除依据 |
|------|---------|
| 排程重叠 | Scout 01:30 不与前一个重叠；且 11-24 峰值并发同为 4 却全部成功 |
| 并发上限 | `agents.maxConcurrent = 4`，11-24 也触及 4，未中止 |
| sessionTarget | 四个失败者**全是 isolated**，而 target=main 的记忆体系讨论任务**成功** → isolated 反而是共同点（推翻 v40 的「isolated 免疫」论断） |
| lease 死锁 | 失败者 scout/life/coder/orchestrator **全部有现役 lease**，差集仍只有 {work} |
| 超时 | 所有 job 的 `timeoutSeconds`/`timeoutMinutes` 均为 None（无显式超时） |
| 重启 | gateway 自 11-23 未重启（不是 RESTART_ABORT） |

**结论：内存压力下，系统回收 worker placement，连带中止在跑的 agent run。**
→ 这与 v30 定位的 RSS 根因（V8 堆 96% 上限 + glibc arena 碎片棘轮）**是同一条因果链的不同表现**：
RSS 涨 → 压力上升 → worker 被回收 → 在跑的 agent run 被中止。
