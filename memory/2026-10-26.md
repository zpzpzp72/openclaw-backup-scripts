## 🔴 01:20 Gateway 内存 10.29GB(34h 未重启)——定位结论:非泄漏,是会话量线性增长

**当前实测**(pid 319857,uptime 1d14h):

| 指标 | 10/24 06:00 基线 | 10/26 01:02 现值 | 变化 |
|------|:---:|:---:|------|

| VmHWM | — | 10.29GB | — |
| anon 映射数 | 9388 | **15194** | +5806 |
| 线程数 | 111 | 127 | +16 |
| 会话文件数 | ~1300(估) | **2571** | ×2 |

**Private_Dirty 拆分(本轮新增)**:anon **9.88GB** / file 0.15GB → 增长全在匿名内存。

**段大小分桶(本轮新增,关键)**:<64KB:105 · **64KB-1MB:15067** · >1MB:533,最大单段仅 73MB。

**回归分析(本轮新增,决定性)**:
```
当前: 15194 映射 / 2571 会话文件 = 5.91 映射·会话
10/24: 9388 映射 / ~1300 会话文件 ≈ 7.2 映射·会话   ← 同一量级!
```
→ **映射数与会话量严格成正比,不是泄漏**。每会话约 6 个 64KB-1MB 匿名段(= 转录/归档在内存里的副本)。

**结论(推翻 MEMORY 10-24 的「外部 Buffer/native 内存膨胀」推测)**:10-24 那次只看了映射数没做比值回归,误以为是 native 膨胀。**实际是每会话固定开销 × 会话数** —— 1.5GB 会话文件时 ~4.9GB RSS,现在 1.6GB agents 目录 / 2571 会话 → 10.29GB。**会话数涨 2 倍,内存也涨 2 倍**。

**实测修正**:MEMORY 里「9388 个 anon rw- 映射」是**映射数**不是字节数;当时据此推断缺证据。本次补齐 Private_Dirty 拆分 + 段大小分桶 + 会话数比值,才算定位到真因。

**可控杠杆(比调 heap 有效得多)**:
- `--max-old-space-size` **调小没用** —— V8 堆只占 496MB,这 9.88GB 在堆外
- **会话转录/归档的保留策略**才是杠杆:清旧会话文件 → 映射数下降 → RSS 下降
- 候选动作:归档/清理 `agents/*/sessions/` 的旧 json(1956 个)+ zst(605 个),或给 gateway 加会话保留上限

**注意**:15067 个 64KB-1MB 段里,`Private_Dirty>0` 的合计 9.88GB,说明这些段**都被写脏了**(不是只 reserve 未 touch)→ 确认是实际数据副本,不是虚拟预留。

- `_versions/*.manifest` = LanceDB 的 **MVCC 版本清单**。每次写操作产生一个新 manifest(354KB,含全量索引与统计)→ 近 1 天新增 **1251 文件 / 0.46GB**
- `data/*.lance` = **活数据分片**,17485 个共 200M → **备份只需这 200M + 最新 manifest**
- 插件**从不调用** `cleanup_old_versions` / `optimize()`(源码 `src/store.ts` 无调用,`cli.ts` 也没有对应子命令)→ 旧版本无限堆积

**官方 API 存在但插件没封装**:`@lancedb/lancedb` 0.26.2 的 `Table.optimize({cleanupOlderThan: Date})`(dist/table.d.ts:41,44,438)专门用于「删除旧版本 + 压实」。插件 `cli.ts` 的 18 个子命令里**没有** optimize/cleanup,`tools.ts` 也只暴露 `memory_recall/store/forget/compact`(compact 是去重压缩,不是 lance GC)。

**结论**:
| 方向 | 动作 | 效果 | 风险 |
|------|------|------|------|
| **A(根治,需 ZP 点头)** | 对 `memories.lance` 调 `optimize({cleanupOlderThan: 某日期})` | 本地释放 ~9G;**每份备份随之从 8.8G 降到 ~0.5G** | 需在插件外直接操作 LanceDB 表,绕过插件封装 → 有风险,必须先备份 data/ |
| **B(备份侧,零风险)** | exclude `.openclaw/memory/lancedb-pro` | 每份 8.8G → ~0.5G(数据仍在本地,不丢) | **备份将不再含向量库** → 恢复后记忆库需重建 |
| **C(保留策略)** | 只留最近 7 份 | 释放 ~220G | 丢历史备份 |

**建议顺序**:先 B+C(立刻止血 NAS),再评估 A(根治)。**A 单独做效果最好** —— 因为 lance GC 后源目录从 20G 缩到 ~11G,备份体积自然回落,不必牺牲备份内容。

**注意**:B 会让备份**不含向量库**(本地仍在),A 会让备份**含精简后的向量库**。两者对「灾难恢复」的意义不同,不可互相替代。
