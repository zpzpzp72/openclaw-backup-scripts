## 本轮三个发现

### 1. ★ 「让 agent 被打开一次」这条路对休眠 agent **走不通**（修正 v39 的乐观假设）

```
$ openclaw sessions archive --agent work --dry-run 'agent:work:recovered:9880f4fe-...'
  archive agent:work:recovered:9880f4fe-...: SQLite session reclamation commit checkpoint expired
```

archive 是**写路径**（走 running gateway），它同样需要 lease；而 lease 又只在写成功后才产生
→ **鸡生蛋死锁**：写需要 lease，lease 需要写成功。

所以对**真正休眠**的 agent（work 的 4 个 session 最新只到 11-23 04:42），
免停机路径不可行。scout 当初能自愈，是因为它**有自己的 cron 每天在跑**
（08:00 那次跑成功了 → 写成功 → lease 顺带产生）。

→ **修正**：自愈的前提是「该 agent 有会成功跑的任务」。没有这个前提，只能走
停机 doctor --fix 或移除 agent。

## WSL 失联 5 天根因：StartWSL2 任务的 72h ExecutionTimeLimit <!-- WSL-SHUTDOWN-72H-KEEPER-20261124 -->
<!-- project: github.com/zpzpzp72/openclaw-backup-scripts -->

### 结论（一句话）
Windows 计划任务 `\StartWSL2`（`wsl.exe -d Ubuntu --exec /bin/sleep infinity`，WSL keeper）的 `ExecutionTimeLimit` 用的是**缺省 PT72H**；2026-11-14 20:06:24 任务启动后跑满 72h 于 **11-17 20:06:24** 被 Task Scheduler 终止（`lastResult=267014`=0x41306=`SCHED_S_TASK_TERMINATED`），15 秒后 **11-17 20:06:39** 发行版收到 poweroff 请求，走**有序关机**（非崩溃/OOM）。之后因该任务只有 LogonTrigger（仅新交互式登录才触发）且期间无新登录，**WSL 再没被拉起，停了 5 天 1.5 小时**，直到 11-22 21:38 才重新 boot。

### 证据链
| 证据 | 实测值 |
|---|---|
| 关机时刻 | boot -1 末条 journal `2026-11-17 20:06:45` (journal stopped)；boot 0 起点 `2026-11-22 21:38:43` |
| 关机性质 | `systemd-logind: The system will power off now!` → `poweroff.target` → `Journal stopped`，gateway 收到 SIGTERM 优雅退出 |
| 排除 OOM/崩溃 | boot -1 内核无 oom/killed process/panic/hung task；无 hung task |
| 排除宿主重启 | Windows `LastBootUpTime = 2026-11-12 02:32:52`（11-17 未重启）|
| 任务与 boot 同步 | `StartWSL2.lastRun = 2026-11-14 20:06:24` = boot -1 第一条 journal 的同一秒 |
| 72h 命中 | lastRun + 72h = 11-17 20:06:24，实际关机 20:06:39（**差 15 秒**）|
| 任务被杀 | `lastResult=267014` = 0x41306 = `SCHED_S_TASK_TERMINATED`（非正常结束）|
| 任务 XML | 无 `<ExecutionTimeLimit>` 元素 → 用缺省 72h |
| 对照 | boot -2（11-08 03:45 结束）**无任何 orderly 关机行** → 那是另一种中断，与本机制无关 |
| 5 天无人拉起 | `StartWSL2` 只有 LogonTrigger + PT20S 延迟；11-14 20:06 → 11-24 16:47 之间 `lastRun` 一直是 11-14，说明**期间无新的交互式登录**（宿主一直开着、登录会话未断）→ 触发器永不重跑 |
| 今天 21:38 | `vmmemWSL pid=33452 start=11/22 21:38:41`，新 boot 0 |

### 为什么你没收到告警（第二个缺陷）
`C:\Scripts\OpenClawHealthCheck.ps1` 每 6h 照常跑、照常报「WSL 响应 ❌」，但**飞书告警全发不出去**：从 10-24 起 `channels.feishu.appSecret` 已改成 SecretRef **对象** `{source:store,id:FEISHU_APP_SECRET}`，脚本仍把它当字符串塞进 JSON → 服务端 `10003 cannot unmarshal object into Go struct field ...app_secret of type string`。日志里累计 **44 次**同样错误（最早 10-19 11:16）。**告警通道本身是哑的。**

### 遗留
- `StartWSL2` 是 LogonTrigger：若 Windows 会话一直不断，keeper 死掉后仍无自动拉起。建议再加一条 `OnIdle`/`Daily` 触发的自愈任务，或把 keeper 改成 `wsl.exe -d Ubuntu --exec sleep infinity` + 任务级 `RestartOnFailure`。
- 备份缺口：11-17 03:08 之后到 11-22 21:38 之间**无任何备份**（NAS 上 11-17 → 11-22 之间空白），期间会话/配置变更全部没有快照。
