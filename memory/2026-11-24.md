## 本轮三个发现

### 1. ★ 「让 agent 被打开一次」这条路对休眠 agent **走不通**（修正 v39 的乐观假设）

```
$ openclaw sessions archive --agent work --dry-run 'agent:work:recovered:9880f4fe-...'
  archive agent:work:recovered:9880f4fe-...: SQLite session reclamation commit checkpoint expired
```

archive 是**写路径**（走 running gateway），它同样需要 lease；而 lease 又只在写成功后才产生
→ **鸡生蛋死锁**：写需要 lease，lease 需要写成功。

所以对**真正休眠**的 agent（work 的 4 个 session 最新只到 11-23 04:42），
免停机路径不可行。scout 当初能自愈，是因为它**有自己的 cron 每天在跑**
（08:00 那次跑成功了 → 写成功 → lease 顺带产生）。

→ **修正**：自愈的前提是「该 agent 有会成功跑的任务」。没有这个前提，只能走
停机 doctor --fix 或移除 agent。

### 2. news-digest 的失败是【另一类】根因

```
11-24 08:04 | error | Context overflow: prompt too large for the model.
                     Try /reset (or /new) to start a fresh session
11-23 08:06 | ok
```

scout **有 lease**，却仍失败 → 与 reclaim 死锁无关，是**上下文过长**。
这正是 v38 议题3 第⑧道闸门预判的形态：「产出落库前先确认落库位置当前可写」
的姊妹问题 —— **产出前先确认上下文还有空间**。

### 3. NAS 24h 掉 175G 的归属：不是备份目录

```
11-23 03:00 可用 373G  →  11-24 03:00 可用 198G（-175G）
同期我方备份目录：19 份(~121G) → 20 份(127.5G)，仅 +6.5G
扫描结果：近 24h 无 >500MB 的新增/修改文件
```

→ **缺口约 168G 不在我方备份目录**，且现已停止下降（连续 3 次实测 192G）。
→ df 已用 7.1T，但 du 可见顶层仅约 222G → **约 6.9T 是 SMB 挂载看不到的占用**
（NAS 侧快照/其它共享/回收站内部），我方无法从 WSL 侧观测或处置。
→ 结论：**NAS 空间问题不在本机可控范围**，需在 NAS 管理界面查快照/配额。
