## 🐛 发现并修正:我的心跳回收站字段有顺序 bug

现象:心跳显示 `recycle_backups=0 recycle_gb=0`,但回收站实际有 **27 份 / 123GB**。

根因:**空间预检在 `cleanup_old` 之前就 `exit 1`** → 回收站检测代码根本没执行 →
变量保持默认 0 → 心跳报 0。
→ 恰好是「最需要告警的场景(空间不足)反而告警不出来」——**告警在最关键时失效**。

修法:把回收站探测提到空间预检**之前**(只读探测,不改任何数据),
让「空间不足」这个错误分支也能带上真实回收站存量。

## 🐛 修复:backup.sh 的 cleanup_old 死锁(11-15 00:30)

### 现象
```
11-06 03:00  ❌ NAS 空间不足: 可用 4G < 需要约 6G —— 跳过备份
11-14 20:06  ❌ NAS 空间不足: 可用 1G < 需要约 6G —— 跳过备份
```
失败日的日志里**只有**空间错误行,**没有**「已移出 N 份」行;而成功日(11-05)有。

### 根因:执行顺序死锁
```
第 306 行  空间预检 → 不够 → exit 1      ← 在这里就退出了
第 366 行  cleanup_old(清理过期备份)      ← 永远到不了
```
→ **空间不够 → 跳过备份 → 不执行清理 → 过期备份不删 → 空间永远不够**。
死锁一旦形成,备份链只能靠人工介入才能解开。

### 修复
把 `cleanup_old` 移到**空间预检之前**。
→ 每次运行都会先按 RETAIN_DAYS 清理,不再因为「没备份成功」而连该清的都不清。

⚠️ 注意:NAS 上 `rm` 是「移入 #recycle」而非真删,清理本身**不释放空间**;
真正释放仍需清空回收站。但至少死锁解开了,后续不会再积累。

```
→ 若它被真删,Avail 4.7MB → ~6.5GB > 阈值 6G,备份可自恢复
→ 但 NAS 上 rm = 移入回收站 → 不释放 → 仍需清空回收站 27 份 / 123GB
```
