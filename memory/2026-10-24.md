## 🔁 06:10 修正：NightOps 的三个结论是错的（Main 复核推翻）

| 结论 | 实测真相 |
|---|---|
| ❌「LiteLLM@NAS DB 挂 400 no_db_connection」 | **探测方法错误**。`openclaw.json` 里 `models.providers.litellm.apiKey` 字面值是 `${LITELLM_MASTER_KEY}`（21 字符，未展开的占位符），我用它直接 curl → LiteLLM 认为 key 无效 → 返回 `No connected db.`。**用 env `LITELLM_MASTER_KEY`（26 字符）实测全部 200**：deepseek-flash 549ms / deepseek-pro 1207ms / LongCat-2.0 1367ms / GLM-5.2 1871ms / Kimi-K2.7 4655ms。`models status` 显示 litellm effective=env `sk-litel...rh6-2007`，运行时本来就用对了 key。 |
| ❌「ollama 是唯一可用 fallback」 | **ollama 根本不存在**。`command -v ollama` 无输出，`127.0.0.1:11434/v1/models` → `http=000` 0.1ms。NightOps 测的 `172.18.160.1:11434` 是 Windows 侧别的东西，不是本地兜底。 |
| ❌「MiniMax M2.7 正常」 | M2.7 与 M3 **同时 429**，错误码 **2056「已达到 Token Plan 用量上限：请升级 Token Plan 套餐或购买积分补充用量」**。这是账号级额度耗尽，不是模型故障。 |

**真正根因**：MiniMax Token Plan 额度用尽 → primary 全挂；而 fallback 第三棒是根本不存在的 ollama，等于**双保险全空**。litellm 一直是好的，只是被误判成死的。
