# 2026-10-30 上午 修 provider 前置条件 / 修 memory-weekly-audit / 查 SQLite checkpoint 故障

## ✅ 1. litellm provider 断链的精确根因(比 10-29 的判断更准)

10-29 我判断「config key 长度 21 vs env key 长度 26」,今天查清了真实机制:

```
openclaw.json → models.providers.litellm.apiKey = '${LITELLM_MASTER_KEY}'   ← 21 字符,是占位符字符串
```
**OpenClaw 没有把 `${...}` 解析成环境变量**,而是把整个字符串当 API key 发出 → LiteLLM 认证失败。

实测对照(同一 endpoint,同一 model):
```
用占位符 '${LITELLM_MASTER_KEY}' → HTTP 400 {"error":{"message":"No connected db.","type":"no_db_connection"}}
用 gateway.systemd.env 的真 key(26字符) → HTTP 200 / 2.25s,正常返回 completion
```
⚠️ `No connected db.` 是 LiteLLM 的**误导性错误文案**,实际含义是「这个 key 不是我的 master key」。

### B 方案的前置条件(今天全部验证通过)
| 条件 | 状态 | 证据 |
|------|:----:|------|
| 真 key 在本机且可读 | ✅ | `~/.openclaw/gateway.systemd.env` → `LITELLM_MASTER_KEY`(26字符) |
| gateway 进程环境确实加载了它 | ✅ | unit 第18行 `EnvironmentFile=-...gateway.systemd.env`;`/proc/<pid>/environ` 实测含该变量 |
| 该变量被标记为 secret 可读 | ✅ | unit 第19行 `OPENCLAW_SERVICE_MANAGED_ENV_KEYS=LITELLM_MASTER_KEY` |
| apiKey 支持 SecretRef 形态 | ✅ | config schema 明确支持 `{source,provider,id}`,`id` 须匹配 `^[A-Z][A-Z0-9_]{0,127}$` |
| 目标形态 | — | `{"source":"env","provider":"default","id":"LITELLM_MASTER_KEY"}` |

**结论**:B 方案可执行,修法 = 把 apiKey 从占位符字符串改成 SecretRef 对象。
**仍需 ZP 明确拍板后才改**(provider 凭据/路由属高影响配置变更)。

影响 3 个任务,每 30 分钟复发一次:
```

10-30 09:38  heartbeat-scout
```
报错原文:**"Sessions remain unavailable. Stop the Gateway, run `openclaw doctor --fix` to inspect and repair this agent database, and restart."**

### 机制(源码定位)
```
dist/session-accessor.sqlite-reclamation-commit-BX3N0u2L.mjs
  const COMMIT_DECISION_TIMEOUT_MS = 5e3;   // 5 秒
  状态机: REQUESTED(5) → COMMITTING(3) → SETTLED(4) / REJECTED(2)
  Atomics.wait(shared, 0, REQUESTED, COMMIT_DECISION_TIMEOUT_MS);
  if (Atomics.compareExchange(shared, 0, REQUESTED, COMMITTING) !== REQUESTED)
      throw new Error("SQLite session reclamation commit checkpoint expired");
```
→ **回收线程请求提交 → 等 owner 主线程在 5 秒内应答 → 超时即报错**。

### 与 RSS 问题的关联(强假设,未证伪)
- gateway 04:16 重启,07:30 首次出现该错误(3 小时后)
- 主线程已累积 **79:47 CPU 时间 / 5.8 小时**(≈23% 均值),明显繁忙
- 回收方:`session-cold-storage-Kd8zP6d_.mjs` / `session-history-eviction-BFbGpe_H.mjs` /
  `session-canonical-validation-readiness-B61y6swg.mjs` —— 都是**会话回收/归档/驱逐**
- main agent sqlite:`session_nodes` 1902 / `transcript_events` 70315 / `trajectory_runtime_events` 15820
- **回收压力源 = 会话表规模**(与 10-30 的 V8 堆 96% 上限、arena 碎片同源:都是会话量累积的后果)

### 误报排除

## 🔴 3b. checkpoint 故障的完整因果链(已闭合)

```
cleanup-service-jgpZZYRh.mjs
  → enforceSqliteSessionHistoryDiskBudget (session-history-eviction-BFbGpe_H.mjs)
    → PHYSICAL_BUDGET_CHECK_INTERVAL_MS = 18e5   ← 30 分钟
      FORCED_PHYSICAL_BUDGET_CHECK_INTERVAL_MS = 6e4 ← 60 秒(强制模式)
    → withSqliteReclamationAuthorization(commitGate, ...) (第 371 行)
      → COMMIT_DECISION_TIMEOUT_MS = 5e3  ← 回收线程等 owner 主线程 5 秒
        → 超时 → throw "SQLite session reclamation commit checkpoint expired"
```
**为什么恰好每 30 分钟复发**:
磁盘预算检查间隔 = 30 分钟,与 heartbeat 周期重合 → 每轮预算检查触发一次回收尝试。
主线程(V8 堆 96% 上限 + 79:47 CPU 时间)经常 5 秒内无法应答 → 必然超时。

**所以这是 RSS/堆压力问题的下游症状,不是独立的数据库故障**:
会话表规模大(main: session_nodes 1902 / transcript_events 70315 / trajectory_runtime_events 15820)
→ 每次预算检查要回收的量大 → 回收耗时长 → 超过 5 秒握手窗口。

**官方修复路径(报错原文给出,需 ZP 执行)**:
```

重启 Gateway                 # 报错明确要求 Stop the Gateway + restart
```
